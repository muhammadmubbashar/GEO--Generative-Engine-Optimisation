10. Implementation checks and their limits

We checked input identity, transformation invariants and delivery to the model. The final FAQ code only converts supported, already-expanded question controls, and checks that the existing answers, offer cards, metadata and links remain unchanged. We rebuilt that stage from the supplied prior-core input and matched all fifty-two saved page outputs. The submission includes the code and offline checker. These are strong implementation checks, but they have a precise scope. They do not certify every inherited fact, remove capture-date differences, or establish that the same pages would be selected by a public AI engine.

11. How an answer becomes a citation score

These are excerpts from the same saved Melbourne-to-London trial. The baseline answer cites source numbers two, three, five and eight. The optimised answer cites two, three and seven. 12. The same pages improved citation in two runs

Here are both generations of the unchanged combined pages. The saved baseline contains one hundred and sixteen citing answers out of two hundred and ninety: forty percent. The initial treatment run contains one hundred and forty-three: forty-nine-point-three percent. The repeat contains one hundred and fifty-two: fifty-two-point-four percent. Relative to the same baseline, those are increases of nine-point-three and twelve-point-four percentage points. We verified that the initial and repeat treatment prompts and sources were identical. The answers still differ because generation varies. Showing both runs is more informative than presenting the higher run as a stable expected rate. Both are development evidence; neither is an independent, untouched confirmation on new customer needs.
